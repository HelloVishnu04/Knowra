1. Executive Summary
OmniRAG is a local-first, model-agnostic AI platform that unifies five distinct knowledge modalities — unstructured documents, live web content, structured SQL data, source code repositories, and controlled tool execution — behind a single conversational and coding interface. Rather than treating retrieval-augmented generation as "one vector database plus one LLM," OmniRAG is architected as an agentic router that classifies each request, selects the correct retrieval pipeline (or combination of pipelines), fuses and reranks evidence, and only then invokes a local language model to synthesize a grounded, citable answer.
This report is the implementation counterpart to the OmniRAG Detailed Engineering Report (v1.0). Where the design report established principles, technology choices and a roadmap, this report specifies exactly how each subsystem is built: concrete PostgreSQL and Qdrant schemas, versioned REST/streaming API contracts, backend module boundaries and class-level responsibilities, the LangGraph state machine used for routing and human-in-the-loop approval, the Docker-based sandbox execution model, the CI/CD pipeline, the evaluation harness, and a phase-by-phase delivery plan with effort estimates and Definition-of-Done gates.
The system is delivered as a modular monolith: one FastAPI application, one Next.js application, and a small set of background workers, all orchestrated with Docker Compose. This keeps operational overhead low during development while preserving clean internal module boundaries (document RAG, web RAG, SQL RAG, code RAG, agents, execution, evaluation) so that any subsystem can be extracted into an independent service later without a rewrite.
1.1 What "Production Level" Means for This Build
Every side-effecting action (file write, code execution, SQL mutation, git commit) is gated behind an explicit human-in-the-loop approval step — never silent agent autonomy.
All retrieval is tenant/workspace-scoped at the query layer, not filtered after the fact — permission checks happen before data reaches the LLM context.
Every answer is traceable end-to-end: request → route decision → retrieved chunks → rerank scores → model call → citations, all persisted with a single run/trace ID.
Code execution never happens in the API process; it always happens inside a disposable, network-disabled, resource-capped container.
Retrieval and routing quality are measured against a golden evaluation dataset (Ragas + custom cases), not judged subjectively.
Secrets are never embedded in source, never injected into LLM context, and are supplied exclusively through environment configuration / secret managers.

This section restates the project objective in implementation-testable terms. Each objective below is paired with a measurable success criterion that Section 15 (Acceptance Criteria) will validate at release.

2.1 Non-Goals for the Initial Release
To keep the MVP shippable, the following are explicitly out of scope for Phases 1–10 and are deferred to the post-MVP backlog (Section 12.1):
Multi-node horizontal scaling / Kubernetes deployment.
MicroVM-grade sandbox isolation (gVisor/Firecracker) — Docker baseline only, documented as a known limitation (Section 8.5).
GitHub/GitLab PR automation (create_pr) beyond local diff review.
OCR / vision-based document extraction for scanned PDFs.
Fine-tuning or training custom models — the platform only serves and routes to pre-trained local/cloud models.

3. System Architecture (Detailed)
3.1 Architectural Style
OmniRAG is built as a modular monolith with a clear internal service-oriented structure. The FastAPI backend hosts all domain modules (document RAG, web RAG, SQL RAG, code RAG, agents, execution, evaluation) as independently testable Python packages that communicate through in-process interfaces, not network calls. Two categories of workload are split out of the API process for latency and safety reasons: (1) background ingestion/indexing jobs run in a queue-backed worker pool, and (2) code/test execution runs in a dedicated sandbox worker that only ever communicates through a job queue — the API process never spawns arbitrary subprocesses itself.

3.4 Data Flow: Single-Source vs. Multi-Source Query
Single-source queries (e.g. "Where is JWT validation implemented?") are routed to exactly one retriever and skip the fusion stage entirely — the retriever's own ranked list is passed straight to reranking. Multi-source queries (e.g. "Compare our revenue with current industry growth") fan out to two or more retrievers concurrently via `asyncio.gather`, and their results are merged with Reciprocal Rank Fusion before reranking. This distinction is decided once, by the router agent, and encoded explicitly in the LangGraph state so it is visible in the trace UI.

5. Data Architecture and Database Design
OmniRAG persists state across three systems with distinct responsibilities: PostgreSQL is the transactional system of record (identity, workspaces, documents, conversations, runs, audit); Qdrant holds vector representations for retrieval; Redis holds ephemeral/cache/queue state; object storage holds original files and execution artifacts. This section defines the concrete schema for each.
5.1 Entity-Relationship Overview
organizations 1──* workspaces 1──* knowledge_bases 1──* documents 1──* document_chunks
                        │                                        │
                        │                                        └──* citations (chunk_id FK)
                        │
                        ├──* repositories 1──* code_symbols
                        │
                        ├──* conversations 1──* messages
                        │                          │
                        │                          └──* retrieval_runs 1──* citations
                        │
                        ├──* agent_runs 1──* tool_calls
                        │                     │
                        │                     └──1 execution_jobs (optional, for run_code/run_tests)
                        │
                        ├──* evaluation_cases    (golden dataset, workspace-scoped or global)
                        ├──* feedback            (thumbs up/down + comment, FK to messages)
                        └──* approvals           (HITL decision log, FK to tool_calls)
 
users *──* workspaces   (membership table: workspace_members, carries role)
5.2 PostgreSQL Schema (Core DDL)
The consolidated, runnable DDL script is provided in Appendix C. The excerpt below highlights the tables central to routing, retrieval traceability and governance — the tables most likely to be referenced during backend development.
-- Multitenancy root
CREATE TABLE organizations (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    name            TEXT NOT NULL,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);
 
CREATE TABLE workspaces (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    organization_id UUID NOT NULL REFERENCES organizations(id) ON DELETE CASCADE,
    name            TEXT NOT NULL,
    settings        JSONB NOT NULL DEFAULT '{}',
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);
 
CREATE TABLE users (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    email           CITEXT UNIQUE NOT NULL,
    password_hash   TEXT NOT NULL,
    display_name    TEXT,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);
 
CREATE TABLE workspace_members (
    workspace_id    UUID NOT NULL REFERENCES workspaces(id) ON DELETE CASCADE,
    user_id         UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    role            TEXT NOT NULL CHECK (role IN ('owner','admin','editor','viewer')),
    PRIMARY KEY (workspace_id, user_id)
);
 
-- Knowledge base / document RAG
CREATE TABLE knowledge_bases (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    workspace_id    UUID NOT NULL REFERENCES workspaces(id) ON DELETE CASCADE,
    name            TEXT NOT NULL,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);
 
CREATE TABLE documents (
    id                  UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    knowledge_base_id   UUID NOT NULL REFERENCES knowledge_bases(id) ON DELETE CASCADE,
    workspace_id        UUID NOT NULL REFERENCES workspaces(id) ON DELETE CASCADE,
    filename            TEXT NOT NULL,
    mime_type           TEXT NOT NULL,
    object_storage_key  TEXT NOT NULL,
    status              TEXT NOT NULL DEFAULT 'pending'
                          CHECK (status IN ('pending','parsing','chunking','embedding','ready','failed')),
    error_message       TEXT,
    created_at          TIMESTAMPTZ NOT NULL DEFAULT now()
);
 
CREATE TABLE document_versions (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    document_id     UUID NOT NULL REFERENCES documents(id) ON DELETE CASCADE,
    version_number  INT  NOT NULL,
    object_storage_key TEXT NOT NULL,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE (document_id, version_number)
);
 
CREATE TABLE document_chunks (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    document_id     UUID NOT NULL REFERENCES documents(id) ON DELETE CASCADE,
    workspace_id    UUID NOT NULL REFERENCES workspaces(id) ON DELETE CASCADE,
    qdrant_point_id UUID NOT NULL,          -- FK by convention into Qdrant, not enforced by Postgres
    chunk_index     INT  NOT NULL,
    page_number     INT,
    section_path    TEXT,                   -- e.g. "3.2 > Refund Policy"
    content_hash    TEXT NOT NULL,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);
 
-- Code RAG
CREATE TABLE repositories (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    workspace_id    UUID NOT NULL REFERENCES workspaces(id) ON DELETE CASCADE,
    name            TEXT NOT NULL,
    default_branch  TEXT NOT NULL DEFAULT 'main',
    source_type     TEXT NOT NULL CHECK (source_type IN ('upload_zip','git_url','local_path')),
    last_indexed_commit TEXT,
    status          TEXT NOT NULL DEFAULT 'pending'
                      CHECK (status IN ('pending','cloning','indexing','ready','failed')),
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);
 
CREATE TABLE code_symbols (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    repository_id   UUID NOT NULL REFERENCES repositories(id) ON DELETE CASCADE,
    file_path       TEXT NOT NULL,
    language        TEXT NOT NULL,
    symbol_name     TEXT NOT NULL,
    symbol_type     TEXT NOT NULL CHECK (symbol_type IN ('function','method','class','interface','module')),
    class_name      TEXT,
    start_line      INT NOT NULL,
    end_line        INT NOT NULL,
    commit_sha      TEXT NOT NULL,
    qdrant_point_id UUID NOT NULL,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX idx_code_symbols_repo_symbol ON code_symbols (repository_id, symbol_name);
 
-- Conversations / traceability
CREATE TABLE conversations (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    workspace_id    UUID NOT NULL REFERENCES workspaces(id) ON DELETE CASCADE,
    user_id         UUID NOT NULL REFERENCES users(id),
    title           TEXT,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);
 
CREATE TABLE messages (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    conversation_id UUID NOT NULL REFERENCES conversations(id) ON DELETE CASCADE,
    role            TEXT NOT NULL CHECK (role IN ('user','assistant','system','tool')),
    content         TEXT NOT NULL,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);
 
CREATE TABLE retrieval_runs (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    message_id      UUID NOT NULL REFERENCES messages(id) ON DELETE CASCADE,
    source          TEXT NOT NULL CHECK (source IN ('document','web','sql','code')),
    query_text      TEXT NOT NULL,
    candidate_count INT NOT NULL,
    fusion_method   TEXT,
    rerank_model    TEXT,
    latency_ms      INT NOT NULL,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);
 
CREATE TABLE citations (
    id                  UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    message_id          UUID NOT NULL REFERENCES messages(id) ON DELETE CASCADE,
    retrieval_run_id    UUID REFERENCES retrieval_runs(id) ON DELETE SET NULL,
    document_chunk_id   UUID REFERENCES document_chunks(id),
    code_symbol_id      UUID REFERENCES code_symbols(id),
    source_label        TEXT NOT NULL,     -- rendered citation text, e.g. "hr_policy.pdf, p.4"
    relevance_score     NUMERIC(5,4),
    CHECK (document_chunk_id IS NOT NULL OR code_symbol_id IS NOT NULL)
);
 
-- Agentic execution + governance
CREATE TABLE agent_runs (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    conversation_id UUID NOT NULL REFERENCES conversations(id) ON DELETE CASCADE,
    route           TEXT NOT NULL,          -- 'document' | 'web' | 'sql' | 'code' | 'multi'
    status          TEXT NOT NULL DEFAULT 'running'
                      CHECK (status IN ('running','awaiting_approval','completed','failed','cancelled')),
    started_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    completed_at    TIMESTAMPTZ
);
 
CREATE TABLE tool_calls (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    agent_run_id    UUID NOT NULL REFERENCES agent_runs(id) ON DELETE CASCADE,
    tool_name       TEXT NOT NULL,
    arguments       JSONB NOT NULL,
    requires_approval BOOLEAN NOT NULL DEFAULT false,
    result          JSONB,
    status          TEXT NOT NULL DEFAULT 'pending'
                      CHECK (status IN ('pending','approved','rejected','executed','failed')),
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);
 
CREATE TABLE approvals (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    tool_call_id    UUID NOT NULL REFERENCES tool_calls(id) ON DELETE CASCADE,
    decided_by      UUID NOT NULL REFERENCES users(id),
    decision        TEXT NOT NULL CHECK (decision IN ('approved','edited','rejected')),
    edited_arguments JSONB,
    decided_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);
 
CREATE TABLE execution_jobs (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    tool_call_id    UUID NOT NULL REFERENCES tool_calls(id) ON DELETE CASCADE,
    kind            TEXT NOT NULL CHECK (kind IN ('run_code','run_tests')),
    container_id    TEXT,
    exit_code       INT,
    stdout          TEXT,
    stderr          TEXT,
    duration_ms     INT,
    network_enabled BOOLEAN NOT NULL DEFAULT false,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);
 
-- Feedback + evaluation
CREATE TABLE feedback (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    message_id      UUID NOT NULL REFERENCES messages(id) ON DELETE CASCADE,
    user_id         UUID NOT NULL REFERENCES users(id),
    rating          SMALLINT NOT NULL CHECK (rating IN (-1, 1)),
    comment         TEXT,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);
 
CREATE TABLE evaluation_cases (
    id                  UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    workspace_id        UUID REFERENCES workspaces(id) ON DELETE CASCADE,
    question            TEXT NOT NULL,
    expected_route      TEXT NOT NULL,
    expected_sources    TEXT[] NOT NULL,
    expected_answer     TEXT,
    created_at          TIMESTAMPTZ NOT NULL DEFAULT now()

5.3 Qdrant Collection Design

6.2 LLM Gateway: Provider Abstraction
Every subsystem depends on the `LLMProvider` interface, never on a specific SDK. The gateway resolves a provider per *role* (fast / coder / strong / embedding / reranker), which is how model routing (Section 6 of the design report) is implemented in code.
# app/llm/base.py
from abc import ABC, abstractmethod
from typing import AsyncIterator
from pydantic import BaseModel
 
class ChatMessage(BaseModel):
    role: str            # "system" | "user" | "assistant" | "tool"
    content: str
 
class ToolCallRequest(BaseModel):
    name: str
    arguments: dict
 
class LLMProvider(ABC):
    @abstractmethod
    async def chat(
        self, messages: list[ChatMessage], *, tools: list[dict] | None = None,
        temperature: float = 0.2,
    ) -> "ChatResult": ...
 
    @abstractmethod
    async def stream_chat(
        self, messages: list[ChatMessage], *, tools: list[dict] | None = None,
    ) -> AsyncIterator[str]: ...
 
    @abstractmethod
    async def embed(self, texts: list[str]) -> list[list[float]]: ...
 
 
# app/llm/gateway.py
class LLMGateway:
    """Resolves a provider instance for a logical model role."""
 
    def __init__(self, settings: "Settings"):
        self._providers = {
            "ollama": OllamaProvider(base_url=settings.OLLAMA_BASE_URL),
            "openai": OpenAIProvider(api_key=settings.OPENAI_API_KEY),
            "anthropic": AnthropicProvider(api_key=settings.ANTHROPIC_API_KEY),
        }
        self._role_map = {
            "fast":       (settings.FAST_PROVIDER, settings.FAST_MODEL),
            "coder":      (settings.CODER_PROVIDER, settings.CODE_MODEL),
            "strong":     (settings.STRONG_PROVIDER, settings.STRONG_MODEL),
            "embedding":  (settings.EMBED_PROVIDER, settings.EMBEDDING_MODEL),
        }
 
    def for_role(self, role: str) -> tuple[LLMProvider, str]:
        provider_name, model_name = self._role_map[role]
        return self._providers[provider_name], model_name
Swapping the entire platform from local to cloud inference is therefore a configuration change: set `FAST_PROVIDER=openai`, `CODER_PROVIDER=anthropic`, etc. No calling code changes, which directly satisfies the "remain model-provider agnostic" objective from Section 2.
6.3 Common Retrieval Contract
# app/rag/base.py
class RetrievedChunk(BaseModel):
    id: str
    content: str
    source: str                 # "document" | "web" | "sql" | "code"
    score: float
    metadata: dict               # page_number, file_path, url, table_name, etc.
 
class RetrievalResult(BaseModel):
    source: str
    query: str
    chunks: list[RetrievedChunk]
    latency_ms: int
 
class Retriever(ABC):
    @abstractmethod
    async def retrieve(
        self, query: str, *, workspace_id: str, top_k: int = 20, filters: dict | None = None,
    ) -> RetrievalResult: ...
`DocumentRetriever`, `WebRetriever`, `SqlRetriever` and `CodeRetriever` all implement this single interface. The router agent and the fusion/rerank stage never need to know which concrete retriever produced a `RetrievedChunk` — this is what makes multi-source fan-out a two-line `asyncio.gather` rather than bespoke merge logic per combination.
6.4 LangGraph Router: State Machine
The router agent is implemented as a LangGraph `StateGraph`. Nodes are pure functions over a shared `AgentState`; edges encode the routing logic; a conditional edge decides single-source vs. multi-source fan-out; an `interrupt()` node pauses execution for human approval before any side-effecting tool runs.
# app/agents/graph.py
class AgentState(TypedDict):
    conversation_id: str
    workspace_id: str
    user_query: str
    route: Literal["document", "web", "sql", "code", "multi"]
    retrieval_results: list[RetrievalResult]
    fused_chunks: list[RetrievedChunk]
    pending_tool_call: ToolCallRequest | None
    approval_status: Literal["not_required", "pending", "approved", "rejected"]
    answer: str
    citations: list[dict]
 
graph = StateGraph(AgentState)
graph.add_node("classify_intent", classify_intent_node)
graph.add_node("plan_route",      plan_route_node)
graph.add_node("retrieve",        retrieve_node)          # fans out internally per route
graph.add_node("fuse_rerank",     fuse_rerank_node)
graph.add_node("generate",        generate_node)
graph.add_node("await_approval",  await_approval_node)    # calls interrupt()
graph.add_node("execute_tool",    execute_tool_node)
graph.add_node("persist_trace",   persist_trace_node)
 
graph.set_entry_point("classify_intent")
graph.add_edge("classify_intent", "plan_route")
graph.add_edge("plan_route", "retrieve")
graph.add_edge("retrieve", "fuse_rerank")
graph.add_edge("fuse_rerank", "generate")
graph.add_conditional_edges(
    "generate",
    lambda s: "await_approval" if s["pending_tool_call"] else "persist_trace",
)
graph.add_conditional_edges(
    "await_approval",
    lambda s: "execute_tool" if s["approval_status"] == "approved" else "persist_trace",
)
graph.add_edge("execute_tool", "persist_trace")
graph.add_edge("persist_trace", END)
 
compiled_graph = graph.compile(checkpointer=redis_checkpointer)
The `await_approval_node` calls LangGraph's `interrupt()`, which persists the full state via the configured checkpointer (Redis-backed for this project) and suspends the run. The `/api/v1/approvals/{id}` endpoint resumes the graph with the human decision, exactly matching the design report's Section 15.2 human-in-the-loop policy.
6.5 Hybrid Retrieval and Reranking Implementation
# app/retrieval/fusion.py
def reciprocal_rank_fusion(
    ranked_lists: list[list[RetrievedChunk]], k: int = 60,
) -> list[RetrievedChunk]:
    scores: dict[str, float] = {}
    chunks_by_id: dict[str, RetrievedChunk] = {}
    for ranked in ranked_lists:
        for rank, chunk in enumerate(ranked):
            scores[chunk.id] = scores.get(chunk.id, 0.0) + 1.0 / (k + rank + 1)
            chunks_by_id[chunk.id] = chunk
    ordered_ids = sorted(scores, key=scores.get, reverse=True)
    return [chunks_by_id[i] for i in ordered_ids]
 
 
# app/rag/document_rag/retriever.py  (hybrid query against Qdrant)
async def retrieve(self, query, *, workspace_id, top_k=20, filters=None):
    dense_vec = await self.embedder.embed_query(query)
    qdrant_filter = build_filter(workspace_id=workspace_id, extra=filters)
    results = await self.qdrant.query_points(
        collection_name="documents_kb",
        prefetch=[
            Prefetch(query=dense_vec, using="dense", limit=top_k * 2, filter=qdrant_filter),
            Prefetch(query=Document(text=query, model="bm25"), using="bm25",
                      limit=top_k * 2, filter=qdrant_filter),
        ],
        query=FusionQuery(fusion=Fusion.RRF),
        limit=top_k,
    )
    return RetrievalResult(source="document", query=query,
                            chunks=[to_chunk(p) for p in results.points], latency_ms=...)
Qdrant's native `Prefetch` + `FusionQuery(fusion=Fusion.RRF)` performs dense+sparse fusion server-side; the application-level `reciprocal_rank_fusion` helper above is reused specifically for the *cross-source* fusion step (document + web + sql + code results combined), where results originate from different systems and cannot be fused inside a single Qdrant query.
6.6 Code Intelligence and Coding Agent
6.6.1 Ingestion Pipeline
Clone/unpack the repository into a scratch workspace; enumerate files, excluding paths matched by `.gitignore`, `node_modules/`, `dist/`, `vendor/`, and binary files.
Detect language per file by extension + Tree-sitter grammar availability.
Parse each file with the matching Tree-sitter grammar; walk the concrete syntax tree to extract function/method/class/interface/module nodes with precise start/end line ranges.
Build a lightweight reference graph (import statements, call expressions) so `find_references(symbol)` can answer without re-parsing.
Embed each symbol's source text (plus a short docstring/signature summary) and upsert into the `code_symbols` Qdrant collection with the payload schema from Section 5.3.
Persist symbol metadata rows into PostgreSQL `code_symbols` for structured queries (e.g. "list all classes in this file").

6.7 Secure Execution Worker
The API process never calls `subprocess` or the Docker SDK directly. `run_code`/`run_tests` tool calls are serialized onto the `queue:sandbox` ARQ queue; a dedicated `worker-sandbox` process — the only component with Docker socket access — consumes jobs and launches one throwaway container per attempt.
# app/workers/sandbox_worker.py  (runs in worker-sandbox container)
async def run_execution_job(ctx, job: ExecutionJobRequest) -> ExecutionResult:
    container = docker_client.containers.run(
        image=f"omnirag-sandbox-{job.language}:latest",
        command=job.command,
        detach=True,
        network_mode="none",                 # no network by default
        read_only=True,
        tmpfs={"/workspace": "size=256m"},
        mem_limit="512m",
        nano_cpus=1_000_000_000,              # 1 CPU
        pids_limit=128,
        user="10001:10001",                  # non-root
        security_opt=["no-new-privileges"],
    )
    try:
        exit_code = container.wait(timeout=job.timeout_seconds)["StatusCode"]
        logs = container.logs(stdout=True, stderr=True)
    except TimeoutError:
        container.kill()
        exit_code, logs = -1, b"execution timed out"
    finally:
        container.remove(force=True)
    return ExecutionResult(exit_code=exit_code, output=logs.decode(errors="replace"))
MVP limitation, documented deliberately
Docker provides CPU/memory/process controls but is not a hard security boundary against a determined kernel-level attacker (per Docker's own engine security documentation). This baseline is appropriate for a portfolio/internal build with trusted or semi-trusted users. Section 8.5 documents the upgrade path (gVisor/Firecracker microVMs) required before accepting untrusted public multi-tenant execution.

7.2 Streaming State Machine
`useChatStream` opens an `EventSource` (or fetch + ReadableStream fallback) against `POST /api/v1/chat` and reduces incoming SSE events into UI state. Event types mirror the backend trace events defined in Section 14 of the design report.
type RunEvent =
  | { type: "run.started"; runId: string }
  | { type: "router.selected"; route: string }
  | { type: "retrieval.started"; source: string }
  | { type: "retrieval.completed"; source: string; candidateCount: number }
  | { type: "reranker.completed"; keptCount: number }
  | { type: "model.token"; token: string }
  | { type: "tool.approval_required"; toolCallId: string; toolName: string; arguments: object }
  | { type: "code.execution.completed"; exitCode: number; durationMs: number }
  | { type: "answer.completed"; citations: Citation[] };
 
function chatReducer(state: ChatState, event: RunEvent): ChatState {
  switch (event.type) {
    case "model.token":
      return { ...state, streamingText: state.streamingText + event.token };
    case "tool.approval_required":
      return { ...state, pendingApproval: event };
    case "answer.completed":
      return { ...state, citations: event.citations, streamingText: "", isDone: true };
    default:
      return { ...state, trace: [...state.trace, event] };
  }
}

Tailwind CSS utility classes only; no ad-hoc CSS files except for Monaco container sizing.
shadcn/ui components are copied into `components/ui/` and customized in place — not treated as an opaque dependency.
All server communication goes through `lib/api-client.ts`, a typed wrapper generated from the backend OpenAPI schema (`openapi-typescript`), so request/response drift is caught at build time.
Markdown answers render through `react-markdown` with a custom citation-link renderer that opens `CitationPopover` instead of navigating away.

8. Security and Governance Implementation
8.1 Authentication and Authorization
Authentication: email + password (Argon2id hashing) issuing a short-lived JWT access token (15 min) and a longer-lived refresh token (7 days), stored as an HttpOnly, Secure, SameSite=Strict cookie.
Authorization: role-based access control at the workspace level (`owner`, `admin`, `editor`, `viewer`) via the `workspace_members` table; every route dependency resolves the current user's role for the target `workspace_id` before executing.
Sensitive routes (`/approvals/*`, `/evaluation/run`, workspace settings) additionally require `admin` or `owner` role.
8.2 Multi-Tenancy Enforcement
Every table that stores tenant data carries a `workspace_id` column (Section 5.2). Every retriever query builds its Qdrant filter from the authenticated user's `workspace_id` before the vector search executes — never as a post-filter on returned results. A dedicated integration test suite (Section 10.2) asserts that a user in Workspace A can never retrieve a chunk whose payload `workspace_id` belongs to Workspace B, even via crafted queries.
8.3 Prompt Injection Defenses
Retrieved content (documents, web pages, code, SQL results) is wrapped in an explicit `<retrieved_evidence>` block in the prompt template and the system prompt states plainly that content inside this block is untrusted data, never instructions.
The LLM is never given the ability to directly invoke tools based on text found inside retrieved evidence — only tool calls emitted through the model's structured tool-call channel (validated against the registered tool schemas) are acted on.
Web-fetched pages are stripped of script/style content and truncated to a maximum evidence length before being placed in context.
8.4 SQL RAG Guardrails
The SQL RAG connection uses a dedicated PostgreSQL role granted `SELECT` only, on an explicit allow-list of tables/views — never the application's primary role.
Generated SQL is parsed into an AST (via `sqlglot`) and rejected if it contains any statement type other than `SELECT`, or references a table outside the allow-list.
Every executed query has an enforced `LIMIT` (default 500 rows) and a statement timeout (default 5s) applied at the connection level.
Any query touching a table tagged `sensitive` in the allow-list configuration requires human approval before execution, even though it is read-only.

8.6 Secrets Management
No secret is ever committed to source control; `.env` is git-ignored and `.env.example` documents required keys with placeholder values only (Appendix A).

Structured logs pass through a redaction filter that scrubs values matching common secret patterns (API keys, bearer tokens, connection strings) before they are written.
8.7 Audit Logging
Every approval decision (`approvals` table), every tool call (`tool_calls` table) and every execution job (`execution_jobs` table) is immutable and timestamped, forming a complete audit trail per conversation. The `audit_service` additionally writes a append-only log entry for workspace membership changes, model configuration changes, and knowledge-base permission edits.

9.4 Production Deployment Topology and Scaling Path
The MVP intentionally ships as a modular monolith on a single host. The scaling path below is documented so growth does not require an architecture rewrite:
Stage 1 (MVP): single host, Docker Compose, one API replica.
Stage 2: horizontally scale the `api` container behind a load balancer once request concurrency requires it; sessions are already stateless (JWT), so this requires no code change.
Stage 3: extract `worker-ingest` and `worker-sandbox` onto dedicated hosts/node pools as ingestion and execution volume grow independently of chat traffic.
Stage 4: split the highest-traffic RAG modality (typically document or code RAG) into its own deployable service once its resource profile diverges materially from the rest of the monolith — enabled by the existing `Retriever` interface boundary (Section 6.3).
Stage 5: move Qdrant/PostgreSQL to managed services and introduce a container orchestrator (e.g. Kubernetes) only once operational overhead is justified by scale.

11.4 Alerting Rules (Baseline)
P95 chat latency > 8s for 5 consecutive minutes → warning.
Error rate > 5% of requests over a 5-minute window → critical.
Sandbox execution timeout rate > 10% over 15 minutes → warning (possible resource starvation or runaway generated code).
Any `agent_runs.status = failed` spike (> 3x rolling baseline) → warning, investigate router/model regression.
Disk usage on Qdrant/Postgres volumes > 85% → warning; > 95% → critical.

Appendix F — Glossary
Term
Definition
RAG
Retrieval-Augmented Generation — retrieving relevant evidence before asking an LLM to generate an answer.
Hybrid retrieval
Combining dense (semantic/embedding) search with sparse (lexical/BM25) search, merged by fusion.
RRF
Reciprocal Rank Fusion — a rank-based method for merging multiple ranked lists into one.
Reranking
Applying a more precise (and more expensive) scoring model to a small candidate set after initial retrieval.
HITL
Human-in-the-Loop — a workflow pause requiring explicit human approval before a side-effecting action proceeds.
Named vector
A Qdrant feature allowing multiple distinct vectors (e.g. dense + sparse) per point in one collection.
Modular monolith
A single deployable application internally organized into clearly bounded modules, enabling later extraction into services.
Sandbox
An isolated, resource-limited, network-disabled execution environment for running untrusted/generated code.
Golden dataset
A curated, versioned set of question/expected-answer cases used to measure retrieval and routing quality objectively.

Final Recommendation
Build order discipline
Build OmniRAG as a local-first modular monolith, exactly in the phase order of Section 12.1 — do not start Code RAG before Document RAG and hybrid retrieval are measurably working, and do not add web/SQL breadth before the router and evaluation harness exist to prove routing quality objectively. Keep model serving behind the LLMGateway interface from day one, make retrieval hybrid before optimizing anything else, enforce tenant permission filters at the retriever layer rather than after generation, require human approval for every side-effecting tool, and treat the golden evaluation dataset as a first-class deliverable — it is what turns "the demo looked good" into a verifiable, production-grade claim.
